# Team memory — Airlinq IoT Platform

Curated index of team-wide learnings. Only Jarvis writes here (promotes `Team-learning candidate` lines from role sign-offs). One line per learning; prune what stops being true.

- Build/deploy gotchas (Windows laptop, air-gapped server) are recorded in `HANDOFF.md` §3, §4.2, §8.6 — read them before any build or deploy.
- Colours always come from `--aq-*` tokens in `ui-ngx/src/styles.scss` (never hex outside the token blocks). The old "no template edits at all" rule is superseded: template/TS edits are allowed when the spec needs structure CSS cannot create, but they must stay additive and merge-friendly (this is a ThingsBoard fork) - see docs/adr/0001.
- A spec is only reachable if the delivery constraint can express it: the dashboard/grid canvas was "implemented" twice under a CSS-only rule that cannot create missing DOM, flip a mode-toggle, or beat inline styles written by TS. Check spec-vs-constraint reachability at G1.
- Theme scoping: `<body class="tb-default">` is STATIC and only `tb-dark` is added on top, so a `.tb-default`-scoped rule also matches in dark; paired token blocks (light 1428 / dark 1478, equal specificity, dark later) flip the colours. A `.tb-default`-only block is a maintainability booby-trap, NOT a dark-mode bug — do not diagnose missing dark styling from the selector alone.
- Repo gates are ALREADY RED on a pristine tree - measure a baseline before coding: `yarn lint` gives 569 problems / 462 errors **as measured on commit `29817200e3` (branch `feature/airlinq-shell-theme-c`, working tree dirty)**; a clean checkout of the same commit measures **567**, so treat any absolute figure as tree-dependent noise and always re-measure a baseline in YOUR tree before coding. ESLint does not lint `.scss`, so an SCSS-only diff cannot move this count at all. It OOMs unless the heap is raised, and `NODE_OPTIONS=--max-old-space-size=8192` is NOT reliably enough: `ng lint` does not always forward it to the ESLint worker and the run dies with SIGABRT `exit code 134`. Invoke node directly instead: `node --max-old-space-size=12288 node_modules/@angular/cli/bin/ng.js lint`, `mvn license:check` had 7 untracked offenders; 4 fixed 2026-09-05 by a pom exclude, 3 remain locally (gitignored `.superpowers/`, invisible to CI), and `netty-mqtt` tests need Docker (absent). Only the before/after DELTA is meaningful; no CI workflow runs `yarn lint`.
- Never run `mvn license:format` blindly here: it would inject Apache headers into the design-canvas `.dc.html` spec artboards under `docs/design/` and corrupt the source of truth. The root pom now excludes `docs/design/**/*.dc.html` (committed spec files) so `license:check` stays green in CI without formatting them. Locally it still reports 3 `Missing header` warnings for gitignored `.superpowers/` files - CI never sees those (gitignore:55), and license-maven-plugin 3.0 has no gitignore-aware option (that is 4.x), so the local red is expected and accepted.
- Adding an entity-table column type needs FIVE coordinated edits: the `EntityTableColumnType` string union, the `EntityColumn` union, the `EntityColumnsType`/`EntityColumnType` `Partial<A & B & C>` intersection the template binds against, every call site's `Array<EntityTableColumn<X>>` widened to `Array<EntityColumn<X>>`, and the `instanceof` filter that builds `entityColumns` in `entities-table.component.ts` (`columnsUpdated()`). Edits 3-4 fail at build time (TS2339 / TS2740); edit 5 fails only at RUNTIME - see the `entityColumns` note below.
- Angular >= 15: a string `[class]="expr"` binding REPLACES the static `class` attribute (silently dropping base classes). Use discrete `[class.foo]="cond"` bindings when a static class must survive.
- `columnsUpdated()` builds TWO arrays that must stay in step: `entityColumns` (filtered by `instanceof`, drives the `matColumnDef` loop in the template) and `displayedColumns` (built from the UNFILTERED config, drives `mat-table`'s row rendering). A column class missing from the `instanceof` filter lands in `displayedColumns` with no matching column def, and `mat-table` throws `Could not find column with id "<key>"` at runtime - it builds clean, lints clean and passes every grep while rendering a broken table. Structural proof is not visual proof: only a browser confirms the table renders.
- Test-criteria applicability must be derived from RUNTIME behaviour, not config flags: `selectionEnabled` is ANDed with the enabled group-action count and Delete is auto-appended, so a flag predicts neither checkboxes nor bulk actions. Likewise `displayPagination=false` is set by no config in this repo.

A same-depth global rule in `styles.scss` LOSES on source order because component styles are injected later. - A rule must live in the stylesheet of the component that **OWNS** the element, or Angular's `_nghost` prefix makes it UNMATCHABLE - one level deeper than the injection-order note above. `:host ::ng-deep` compiles to `[_nghost-<thisComponent>] <selector>`, so a rule written in component A can never reach an element rendered by component B's template, however specific it looks. Read the `_nghost`/`_ngcontent` attribute off the REAL element to find the owner: on the rail, `tb-side-menu` is `_nghost-ng-c3162484443`, but the nav anchor belongs to `tb-menu-link` (`_nghost-ng-c925066261`, `menu-link.component.html:18`), the section TILE to `tb-menu-toggle` (`_nghost-ng-c2149650991`, `menu-toggle.component.html:18`), and the wordmark to `home.component` (`_ngcontent-ng-c935555661`) - four owners for one visual surface, while `.tb-menu-section` really is tb-side-menu's. A G3 BLOCKER shipped because the fix sat in `side-menu.component.scss`. - `Team-learning candidate:` A CSS rule that WINS the cascade can still paint the wrong pixel, because `opacity` on the element composites the winning colour afterwards. `getComputedStyle().color` returns the DECLARED value and therefore AGREES with the stylesheet - so this defect class is invisible to computed-style assertions, which is how a "9.30:1" claim survived review while the browser painted 7.22:1. Any contrast evidence for an element under an `opacity` (breadcrumb anchors and `.divider` at `breadcrumb.component.scss:42,63`) must flatten colour x opacity against the surface. Sweeps that compare declared fg vs bg cannot see it; add painted rows.

- `Team-learning candidate:` `.tb-default:not(.tb-dark)` does NOT automatically outrank a component rule. Angular compiles `:host` to an attribute selector that counts as a CLASS, so a component rule nested a few levels reaches ~(0,5,1) AND is injected after `styles.scss`, winning equal-specificity ties too. `user-menu.component.scss:182` (~(0,5,1)) beat a global N12 at (0,3,0) outright, leaving the rail authority line at `--aq-text-3` `#6b7789` = 3.97:1 on `#0a1435` - an AA FAIL that looked fixed. - `Team-learning candidate:` `:last-child` is a trap in a wrapped list. In the breadcrumb every parent `<a>` is the ONLY child of its own wrapper `<span>`, so `a:last-child` matches EVERY parent, not the final entry - and at (0,4,2) it outranks the sibling parents rule at (0,4,1), painting all parents with the current-entry ink and silently merging two tiers of a three-tier ramp. Same trap in the other direction: `span:not(.divider)` also matches those wrapper spans, and since the component sets `color: inherit` on the anchor, the anchor then inherits the wrapper's ink. Select the class-less current entry as `span:not([class])`. Both errors were found only by asking the browser which rules matched, never by reading the file.
- A CSS rule must live in the stylesheet of the component that OWNS the element: Angular compiles `:host`/`::ng-deep` with that component's `_nghost` prefix, so a correctly-written rule in a NEIGHBOURING component's file is unmatchable. Corollary: an ANCESTOR class needs `:host-context()`, never a descendant inside `:host ::ng-deep`. This is one level deeper than the injection-order note above.
- The cascade winner may be Material's OWN generated CSS, present in no source file (e.g. `.mat-toolbar .mat-mdc-button-base.mat-mdc-button-base.mat-unthemed` at (0,4,0), where the duplicated class is Material's deliberate specificity-bump idiom and counts twice). Fetch the compiled `styles.css` over HTTP and regex it; `document.styleSheets` scans miss `<link>`ed sheets and report zero hits for a rule that is demonstrably winning.
- `getComputedStyle` can be RIGHT while the painted pixel is WRONG for three distinct reasons now recorded here: `opacity` compositing, a gradient's varying width, and a Z-INDEX SIBLING that paints over the element (the `/home` navy lives on `div.mat-fab-toolbar-background`, z-index 21, so an ancestor-walking `bgOf()` reported `#eeeeee` and produced 8 false failures while nearly masking 2 real ones). - Specificity analysis is insufficient for an element with no competing DIRECT colour declaration: a direct declaration beats an inherited value regardless of specificity, so a rule that safely loses on anchors (which declare `color: inherit`) still wins on their sibling dividers and text spans. Check for a direct competitor per ELEMENT, not per selector. Related: a `color: inherit` child can be intercepted by an ancestor INSIDE its own component (`.entity-state-controller { color: rgba(0,0,0,.76) }`), making a shell-level ancestor rule irrelevant.
- When an `!important` declaration owns an element and adding one is forbidden, re-point the TOKEN that winning declaration reads, scoped to a container. Cost: it moves every consumer inside that container, so the enumeration must be exhaustive and each out-of-scope consumer individually checked against the container's template - never dismissed by category.
- A component's `@if`/`@else` branches keyed on `isMobile` are TWO separate styling surfaces, and a desktop-only verification pass is structurally blind to the mobile one. `entity-state-controller` produced the same 1.33:1 defect twice for this reason (desktop spans, then mobile `h1` + `mat-select`). Also: `stateObject` is the breadcrumb STACK, not the dashboard's state COUNT - a 3-state dashboard still renders the `<h1>` branch until you drill into a child state.
- A light-only rule qualified with a chrome container class must NOT also be emitted unqualified "for safety" - the unqualified twin reaches every other surface, and chrome ink on the light sheet is a 1.2-2.0:1 invisibility regression. Scope once, deliberately. `<tb-breadcrumb>` has three instances and only `home.component.html:63` is inside `.tb-primary-toolbar`.
- Hash conventions must be published with the digest or they are not reproducible: the same range yields different sha256 with/without the trailing newline, and on this CRLF worktree a raw read differs from `git show`'s UTF-8/LF. Canonical convention for the frozen dark block (docs/requirements/airlinq-blue-light-recolour.md §9d): UTF-8 -> normalise CRLF to LF -> brace-match the SECOND top-level `.tb-dark {` (never hard-code line numbers; the block moves) -> join with `\n`, no trailing newline -> sha256 = `788af402f02081504d0d05bef6184adab6a60447722c2cbbb0aeeb3eb10622bf`. `styles.scss` has TWO top-level `.tb-dark` blocks (tokens, then rules) plus a shared `.tb-default` block that also matches in dark.
- "Additive" invariants are measured against HEAD, never against a mid-cycle working state - the latter exists in no commit and is not a reviewable baseline. Verify additivity by DECLARATION NAME AND VALUE, not by `git diff` +/- line counts, which report unchanged declarations as removed-and-re-added.

- A DESCENDANT selector is never satisfied by two classes on the SAME element: `.tb-dark .mat-app-background` needs a `tb-dark` ANCESTOR. - Dart Sass rejects a suffix `&` ("may only be used at the beginning of a compound selector"); the construct is `@at-root body#{&}`. `@at-root` hoists past parent SELECTORS but stays INSIDE enclosing at-rules, so it is safe within `@media` - verify by compiling against the repo's own `node_modules/sass`, never by reasoning.
- When a frozen-block edit changes only a rule's SELECTOR WRAPPER, compare the block's DECLARATION MULTISET (name+value) rather than its hash: an empty multiset diff is a stronger and cheaper no-op proof than a pixel diff, and it survives the digest necessarily changing. - Screenshot comparison confounds that cost real time here: `:hover` follows the mouse ACROSS navigation (one hovered table row = 74k phantom pixels), so park the pointer, blur focus, assert zero hovered rows, and set `reducedMotion: 'reduce'` on every capture.
- `mat-button` projects ALL unslotted content into ONE `span.mdc-button__label`, and `class="material-icons"` matches Material's FIRST projection slot, emitted BEFORE that label. So an icon carrying `material-icons` is hoisted ahead of its siblings REGARDLESS of template order - the user-block overflow glyph rendering left of the avatar was projection-slot order, not a cascade fault. The fix is the `iconPositionEnd` attribute (already used at 9 sites here), not CSS `order`/`margin-left: auto`. Corollary: before diagnosing a mis-ordered `mat-button` child as a flex/cascade problem, check which projection slot its classes select.
- A widget's `autoScale` shrinks text by `transform: scale()`, NOT by font-size: `value-card-widget.component.ts:148-215` runs a `ResizeObserver` that computes `scale = min(panelW,panelH)/squareLayoutSize` and calls `renderer.setStyle(content,'transform',...)` at :215 (`autoScale` defaults TRUE). A CSS `min-font-size` therefore CANNOT rescue illegible tile text - the transform multiplies whatever is declared, so an 11px label inside `scale(0.55)` still paints ~6px. Measure the CUMULATIVE TRANSFORM CHAIN, not the declared size, and fix by clamping the scale floor, disabling autoScale, or raising stored sizes so the post-scale product clears the floor.
- Specificity MUST be measured on the COMPILED selector, never the authored SCSS. Angular emits `[_ngcontent-%COMP%]` PER NESTING LEVEL, and each is an attribute selector that counts as a CLASS - so a rule nested two levels deeper silently gains two class-levels. On the rail head this made `display: flex` (0,9,1) BEAT the two-class collapse rule `display: none` (0,8,2), because class count outranks type count. An authored-SCSS reading gave the opposite answer twice (the architect's design AND Jarvis's own independent check) and would have shipped a no-op fix. Read the matched-rule list off the live element, or grep the built component CSS out of `ui-ngx/target/generated-resources/public/*.js`.
- `ng serve` can serve a STALE lazily-loaded chunk indefinitely: a verified-correct source edit measured as entirely absent at runtime (scale tracked `innerMin/160` with no plateau) while the production bundle contained the floor all along. For lazy widget code, verify against `target/generated-resources/public/`, and treat a dev-server measurement that contradicts a confirmed source edit as a stale-chunk symptom, not a failed fix.
- `iconPositionEnd` fixes projection ORDER but not trailing ALIGNMENT: Material's `span.mdc-button__label` is `flex: 0 1 auto`, so a `flex: 1 1 auto` child INSIDE it never claims the BUTTON's free space (106.2px of slack measured, glyph parked mid-button). Trailing alignment needs `margin-left: auto` on the glyph itself. Order and position are two separate defects on one element - fixing one does not imply the other.
- Below `gt-sm` this shell's rail becomes an `over`-mode drawer parked OFF-SCREEN (x=-250/-334) with a 0x0 element box, so a clipping defect cannot reproduce there even though the collapse rule also cannot match. A narrow-vs-desktop split can be decided by the drawer MODE, not the breakpoint rule - measure the element's box, not just which classes are present.
- `menu-toggle.component.html:66` renders every child unconditionally as `<tb-menu-link>` with NO child `@switch`, so a toggle nested inside a toggle renders as a flat link and SILENTLY LOSES its grandchildren. The menu tree must stay `heading -> toggle -> link`. Worse, `sectionHeight()`'s `pages.length * 40` would be accidentally RIGHT while the content is wrong, so the height maths is not the tell - assert structurally that no toggle has a toggle descendant.
- A FOURTH way `getComputedStyle` is right while the pixel is wrong: an ANCESTOR's `opacity: 0` (joining opacity-compositing, gradient width, and z-index siblings). - `box-sizing: content-box` is never an "axis" choice - it applies to BOTH. On the rail-foot user block it was load-bearing on the block axis (AC-15's 56px = 12+32+12) while silently breaking the inline axis by 28px: `width: 100%` resolved to the full 250px rail with padding added OUTSIDE, giving a 278px border box in a 250px rail. Fix one axis with `width: calc(100% - <padding-left + padding-right>)`; flipping `box-sizing` fixes one axis and breaks the other in the same stroke. A declared `width: 100%` reveals neither - check `computedWidth` AND the border box.
- A CORRECT `margin-left: auto` can park an element outside its container: it aligns to the border box's trailing edge, so an overflowing border box carries the child out with it (glyph landed 16px past the rail, clipped by THREE nested `overflow: hidden` ancestors, `elementFromPoint` returning the dashboard). "Element is past the edge" and "flex alignment is broken" are indistinguishable from the element's own rect - measure against the CONTAINER's rect, not the parent's content box.

- A `width` that compensates padding is STATE-COUPLED: it silently becomes wrong in any state that changes that padding. `box-sizing: content-box` forces this pattern (the border box cannot do the arithmetic), so every `width: calc(100% - Npx)` under `content-box` needs a matching reset in each state whose inline padding differs.
